## 고칠 항목 (blocker, major)
### SEC-1: 약한 SECRET_KEY와 APP_PASSWORD로도 앱이 동작한다
- 등급: major. 공개 배포와 약한 값이라는 조건이 필요하다. 약한 키 하나로 비밀번호와 실패 제한을 모두 우회하고, 서버 저장이 없어 위조 토큰을 키 교체로만 끊을 수 있다.
- 위치: src/app/settings.py:11-12, src/app/auth.py:18,28,33, src/app/routers/auth.py:30,46
- 문제: 빈 값은 안전하게 막지만 길이나 공백뿐인 값은 검사하지 않는다. 저장소가 공개되어 salt와 페이로드 형식도 공개됐고 비밀로 남은 것은 `SECRET_KEY`뿐이다. 쿠키 검증에는 횟수 제한이 없다.
- 악용 시나리오: 공개 배포에서 `SECRET_KEY`가 추측 가능하면, 외부인이 제한 없이 키를 맞혀 토큰을 위조하고 비밀번호 없이 모든 데이터를 읽고 고친다. `APP_PASSWORD`가 약하면 IP당 하루 약 7,200회로 사전 대입이 가능하다.
- 완료 기준: `SECRET_KEY`나 `APP_PASSWORD`가 비었거나, 공백뿐이거나, 설계 보완 1번에서 정한 최소 길이보다 짧으면 앱이 시작되지 않고 원인을 로그에 남긴다. 테스트 전용 설정은 이 검사를 받지 않거나 기준을 만족하는 값을 쓴다. 기준을 만족하는 값이면 지금과 같이 시작한다.
- 관련 기능: F5
- 지적한 담당: B, C

### SEC-2: 요청 본문 크기 상한이 없다
- 등급: major. 공개 배포와 상한 없는 앞단이라는 조건이 필요하다. 미로그인 외부인이 닿는다.
- 위치: src/app/main.py:50-60, src/app/schemas.py:22-23
- 문제: FastAPI는 의존성 실행 전에 본문을 읽는다. 그래서 `/api/login`뿐 아니라 로그인이 필요한 POST·PATCH도 미로그인 상태에서 본문 전체를 메모리에 읽고 파싱한다. `password`에도 길이 상한이 없다.
- 악용 시나리오: 공개 배포에서 미로그인 외부인이 `Content-Type: application/json`으로 큰 본문을 동시에 보내 프로세스 메모리를 소진시켜 서비스를 멈춘다.
- 완료 기준: 설계 보완 2번에서 정한 상한보다 큰 본문을 보낸 POST·PATCH는 로그인 여부와 무관하게 공통 오류 모양으로 거부되고 핸들러에 닿지 않는다. 상한 이하의 가장 큰 정상 노트(본문 50,000자)는 지금처럼 저장된다. `password`가 정해진 길이를 넘으면 비교 없이 거부된다.
- 관련 기능: F5, F1, F2, F3
- 지적한 담당: C (A, B도 같은 경로를 언급)

### SEC-3: 쿠키 Secure가 요청 판정에 달려 있다
- 등급: major. HTTPS 배포와 프록시 설정 누락이라는 조건이 필요하다. 토큰은 30일 유효하고 서버에서 폐기할 수 없으며, 실패해도 오류가 나지 않아 눈에 띄지 않는다.
- 위치: src/app/routers/auth.py:20-21,57,68
- 문제: `Secure`를 `request.url.scheme`으로 정한다. 프록시 헤더가 빠지거나 신뢰되지 않으면 HTTPS 배포에서도 조용히 `Secure` 없는 쿠키가 나간다. HSTS도 없다.
- 악용 시나리오: 그런 배포에서 사용자가 http 주소로 한 번 접속하면, 같은 네트워크의 공격자가 쿠키를 가로채 로그아웃과 무관하게 30일간 재사용한다.
- 완료 기준: 공개 배포용 설정을 켜면 프록시 헤더가 없는 요청에도 로그인 응답의 `Set-Cookie`에 `Secure`가 붙는다. 설정을 끈 로컬 실행에서는 지금처럼 http로 로그인된다. 로그아웃 쿠키도 같은 속성을 쓴다. running.md에 이 설정과 HSTS를 적는다.
- 관련 기능: F5
- 지적한 담당: B, C

### SEC-4: 프록시 설정에 따라 로그인 잠금이 무력화되거나 공유된다
- 등급: major. 프록시 뒤 배포라는 조건이 필요하다. 조건이 맞으면 비밀번호 대입 제한이 사라진다.
- 위치: src/app/auth.py:97-98, docs/service/running.md:33-43, docs/impl-reports/SUMMARY.md:32
- 문제: 잠금 키 `request.client.host`는 uvicorn이 `X-Forwarded-For`로 바꾼 값이다. `--forwarded-allow-ips='*'`이면 맨 왼쪽 값을 그대로 믿고, 신뢰한 프록시가 그 헤더를 덮어쓰지 않아도 클라이언트 값이 쓰인다. uvicorn 0.54는 프록시 헤더가 기본으로 켜져 있고 127.0.0.1과 ::1을 신뢰하므로 같은 서버의 프록시는 옵션이 없어도 해당한다. 반대로 프록시가 신뢰되지 않으면 모두 프록시 IP 하나로 묶인다. running.md와 SUMMARY.md의 "옵션이 없으면 한 IP로 묶인다"는 프록시가 루프백이 아닐 때만 맞고, 프록시가 보내야 할 헤더는 적혀 있지 않다.
- 악용 시나리오: 헤더를 믿는 설정이면 외부인이 요청마다 값을 바꿔 5회 제한 없이 비밀번호를 시도하거나 주인의 IP를 지정해 잠근다. 모두 한 IP로 묶이면 60초마다 5번 틀려 주인의 새 로그인을 계속 막는다.
- 완료 기준: 신뢰하지 않은 주소에서 온 요청의 `X-Forwarded-For`를 바꿔도 같은 잠금 카운터가 쓰여 6번째 시도가 429다. running.md에 프록시가 `X-Forwarded-For`와 `X-Forwarded-Proto`를 덮어써야 한다는 것, `'*'` 금지, 동작 확인 방법이 있다. 부정확한 문장을 고친다.
- 관련 기능: F5
- 지적한 담당: B, C (A는 info로 언급)

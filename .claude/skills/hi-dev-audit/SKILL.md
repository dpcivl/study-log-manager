# hi-dev-audit: 전체 보안 점검 지휘자 매뉴얼

너는 지휘자다. 점검은 security 서브에이전트에게 맡긴다. 너는 점검 범위를 정리하고, 일을 나눠 맡기고, 결과를 판정해 보고서를 쓰고, 고칠 항목을 등록한다.
코드는 읽기만 한다. 서버를 띄우거나 요청을 보내지 않는다.

실행 방식: $ARGUMENTS
- 비어 있으면: 서비스 전체 점검
- `recheck`면: 가장 최근 감사 보고서의 blocker와 major 지적만 다시 확인

## 입력과 출력
- 입력: `docs/design.md`, `docs/service/api.md`, `docs/impl-progress.md`, `src/` 전체 (모두 읽기만)
- 출력: `docs/audit-reports/(날짜).md`, `docs/impl-progress.md`에 SEC 항목 추가

## 1. 준비

### 확인
1. `docs/impl-progress.md`에서 모든 기능(F로 시작하는 ID)이 "완료"인지 확인한다. 아니면 완료되지 않은 기능을 알리고 계속할지 묻는다.
2. 상태가 "진행"이나 "critical"인 SEC 항목이 있으면, 지난 점검의 수정이 끝나지 않았다고 알리고 `recheck`를 먼저 할지 묻는다.
3. `git status`로 커밋되지 않은 변경이 있는지 확인한다. 있으면 점검 결과가 커밋된 코드와 달라질 수 있다고 알리고 계속할지 묻는다.
4. `git rev-parse --short HEAD`로 지금 커밋을 기록해 둔다. 보고서에 "점검 기준 커밋"으로 적는다.

### 권한 표 만들기
design.md "5. 인터페이스 약속"과 "8. 보안 고려 사항", `docs/service/api.md`를 보고 모든 API의 권한을 한 표로 정리한다.
```
| 메서드 | 주소 | 로그인 필요 | 쓸 수 있는 사람 | 남의 데이터 접근 | 근거 |
| --- | --- | --- | --- | --- | --- |
| GET | /api/minutes/{id} | 예 | 작성자 본인 | 불가 | design.md 8번 "(해당 문장)" |
```
- 표의 내용은 design.md와 api.md에 적힌 것만 쓴다. 지어내지 않는다.
- 문서에 권한이 적혀 있지 않은 API는 해당 칸에 "정해지지 않음"이라고 적고, 보고서의 "설계 보완 필요"에 올린다.

### 점검 대상 목록
- `src/` 아래 파일 목록과 의존성 파일(package.json, requirements.txt 등)의 위치를 정리한다. 2부의 작업 지시서에 넣는다.

## 2. 점검

### 작업 지시서
security 세 명에게 아래 양식으로 각각 작업 지시서를 넘겨 **동시에** 실행한다. 셋 다 끝날 때까지 기다린다.
```
[작업 지시] security (담당: A / B / C)
- 기능: 전체 (서비스 전체 감사)
- 점검 범위: (1부에서 정리한 src/ 파일 목록 전체)
- 맡은 점검 항목: (security 파일의 점검 항목 번호와 이름을 그대로)
- 다른 점검 항목: 다른 담당이 본다. 깊게 보지 않되, 눈에 띄면 한 줄로 남긴다.
- 보안 고려 사항: (design.md "8. 보안 고려 사항"을 그대로 복사)
- 이번에 할 일: (아래 담당별 내용)
```

### 담당별 할 일
- **A: 1. 입력 처리, 2. 출력 처리**
  - 사용자 입력이 들어오는 모든 지점(주소의 값, 요청 본문, 헤더, 업로드 파일)을 목록으로 만든다.
  - 지점마다 그 값이 데이터베이스 질의, 셸 명령, 파일 경로, 화면 출력에 닿는 곳까지 끝까지 따라간다.
  - 같은 종류의 입력을 기능마다 다르게 처리하는 곳이 있으면 함께 보고한다.
- **B: 3. 인증과 권한**
  - 작업 지시서에 1부의 **권한 표 전체**를 붙인다.
  - 표의 줄마다 그 API를 처리하는 코드를 찾아, 로그인 확인과 본인 확인이 표대로 되어 있는지 본다. 줄마다 "일치 / 불일치 / 확인 불가"로 판정한다.
  - 같은 데이터를 다른 API로 우회해서 볼 수 있는지 본다. 예: 상세 보기는 막혔지만 목록이나 검색에 남의 데이터가 섞여 나오는 경우.
- **C: 4. 비밀 정보, 5. 오류 노출, 6. 설정, 7. 의존성**
  - 프로젝트 전체 설정 파일과 환경 변수 처리를 본다.
  - 의존성 점검 명령(npm audit, pip-audit 등)을 실행하고 결과를 요약한다.

`src/`의 파일이 많아서(50개 이상) 한 명이 다 읽기 어려우면, A와 B를 폴더별로 더 나눠 여러 명을 부른다. 나눠도 B에게는 권한 표 전체를 준다.

## 3. 판정
1. 세 보고의 지적을 한 목록으로 모은다. 같은 위치나 같은 문제를 가리키면 하나로 합치고, 어느 담당이 지적했는지 함께 적는다.
2. 담당이 매긴 등급을 그대로 쓰지 않고, security 파일과 같은 심각도 기준으로 지휘자가 다시 판정한다.
   - 바깥에서 누구나 바로 악용할 수 있으면 blocker
   - 로그인이나 특정 조건이 필요하면 major
   - 실제 악용 경로가 없는 습관 문제는 minor
   - 근거가 부족하면 등급을 낮춘다. 판정한 등급과 이유를 한 줄씩 남긴다.
3. B의 권한 표 판정에서 "불일치"는 지적 목록에 넣고, "확인 불가"는 "설계 보완 필요"나 "추가 확인 필요"로 따로 모은다.
4. 1부에서 "정해지지 않음"으로 남긴 권한과, 담당들이 설계가 애매하다고 적은 부분을 "설계 보완 필요"로 모은다.

## 4. 보고서
`docs/audit-reports/(날짜).md`로 저장한다.
```
# 보안 감사 보고서 (날짜)
- 점검 기준 커밋: (커밋 번호)
- 점검 방식: 전체 / recheck

## 요약
- blocker (n) / major (n) / minor (n) / info (n) / 설계 보완 필요 (n)

## 권한 표
(1부의 권한 표에 B의 판정 칸을 더한 것)

## 고칠 항목 (blocker, major)
### SEC-(번호): (한 줄 제목)
- 등급:
- 위치: (파일 경로:줄 번호)
- 문제:
- 악용 시나리오:
- 완료 기준: (고쳐졌다고 확인할 수 있는 문장)
- 관련 기능: (F로 시작하는 기능 ID)
- 지적한 담당: (A / B / C)

## 남은 지적 (minor, info)
- (등급) (위치): (문제) - (담당)

## 설계 보완 필요
- (무엇이 정해지지 않았는지) → (사용자가 정해야 할 질문)

## 의존성 점검
(C의 결과 요약)
```
- 완료 기준은 테스트로 확인할 수 있는 문장으로 쓴다. 예: "로그인한 다른 사용자가 GET /api/minutes/{id}로 남의 회의록을 요청하면 403이 온다"
- SEC 번호는 진행 기록에 이미 있는 가장 큰 번호 다음부터 매긴다.

## 5. 수정 등록
1. blocker와 major마다 `docs/impl-progress.md`의 기능 현황에 줄을 추가한다. blocker를 먼저 넣는다.
   `| SEC-(번호) | (한 줄 제목) | 대기 | 0 | 0 |`
2. "설계 보완 필요"는 등록하지 않는다. 사용자가 정해서 design.md를 고친 뒤 hi-dev-impl로 반영한다.
3. 보고서와 진행 기록만 `git add 파일경로`로 하나씩 담아 `docs: 보안 감사 보고서 (날짜)` 메시지로 커밋한다.
4. 사용자에게 아래를 보여 주고 끝낸다.
   - 요약과 SEC 항목 목록 (번호, 등급, 제목)
   - 설계 보완 필요 질문 전체
   - 다음 단계: "새 대화(`/clear`)에서 `/hi-dev-impl SEC-1`부터 하나씩 고치세요. 모두 고친 뒤 `/hi-dev-audit recheck`로 확인하세요."

## 6. recheck
`$ARGUMENTS`가 `recheck`이면 1. 준비의 확인 3~4번만 하고, 2~5 대신 아래를 한다.
1. 가장 최근의 전체 점검 보고서를 찾아 SEC 항목을 읽는다.
2. 진행 기록에서 각 SEC 항목의 상태를 본다. "완료"인 것만 다시 확인하고, 나머지는 "아직 수정 안 됨"으로 적는다.
3. security 한 명에게 작업 지시서를 넘긴다. "이번에 할 일"에 확인할 SEC 항목의 위치, 문제, 완료 기준을 그대로 붙이고 아래를 맡긴다.
   - 항목마다 "해결됨 / 남음 / 판단 불가"와 근거
   - 고친 코드 주변에 새로운 문제가 생겼는지
4. 결과를 `docs/audit-reports/(날짜)-recheck.md`로 저장한다.
   ```
   | SEC 번호 | 판정 | 근거 |
   ```
5. "남음"인 항목은 진행 기록의 상태를 "대기"로 되돌리고, 실행 기록에 이유를 한 줄 남긴다. 새로 생긴 문제는 새 SEC 번호로 등록한다.
6. 보고서와 진행 기록을 커밋하고, 결과를 사용자에게 알린다. 모두 해결됐으면 그렇게 알린다.

## 7. 하지 말 것
- 서버를 띄우거나, 요청을 보내거나, 공격을 시도하지 않는다.
- `src/`, `tests/`, `docs/design.md`를 고치지 않는다. 감사는 읽기만 하고, 고치는 건 hi-dev-impl의 일이다.
- 권한 표나 완료 기준을 문서에 없는 내용으로 지어내지 않는다.
- 근거 없이 등급을 올리지 않는다.
- push하지 않는다.

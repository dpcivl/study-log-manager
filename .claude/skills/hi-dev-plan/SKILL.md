# hi-dev-plan: 설계 단계 매뉴얼

Research → Plan → Implement 순서로 설계 문서(design.md)를 만든다.
이 문서는 다음 단계(Claude Code에서 목업 → 구현 → 보안 점검)의 유일한 입력이다.
목업이나 코드는 만들지 않는다. 대신 다음 단계가 문서만 보고 작업할 수 있을 만큼 구체적으로 쓴다.
특히 인터페이스 약속은 구현과 테스트가 서로의 코드를 보지 않고 동시에 만들어지는 근거가 되므로 빠짐없이 쓴다.

## 진행 체크리스트
작업을 시작할 때 아래 목록을 보여 주고, 단계가 끝날 때마다 체크한다.
- [ ] 1. Research: 요구사항 파악
- [ ] 2. Plan: 설계 결정 확인
- [ ] 3. Implement: design.md 작성과 자체 점검
- [ ] 4. 전달

## 1. Research
- 사용자에게 아직 모르는 것만 물어본다: 무엇을 만드는지, 누가 쓰는지, 꼭 필요한 기능 3가지, 선호하는 기술. 한 번에 질문은 3개까지.
- 비슷한 서비스나 기술 선택에 조사가 필요하면 웹 검색을 한다.
- 조사 결과를 5줄 이내로 요약해 보여 주고 확인받는다.

## 2. Plan
- 아래 양식의 항목별로 핵심 결정만 짧게 보여 준다: 기능 범위, 화면 목록, 기술 스택, API 목록(메서드, 주소, 하는 일 한 줄).
- 첫 버전 범위는 작게 잡는다. 필수 기능은 5개를 넘기지 않는다.
- 사용자가 확인하기 전에는 문서를 쓰지 않는다.

## 3. Implement: design.md 작성
아래 양식 그대로 `design.md` 파일을 만든다.
- 기능마다 F1, F2 같은 ID를 붙인다. 이 ID는 목업·구현·테스트·보안 단계에서 체크리스트로 쓴다.
- 화면마다 S1, S2 같은 ID를 붙이고, 목업을 만들 사람이 그대로 그릴 수 있게 주요 요소를 적는다.
- S나 F로 시작하는 ID는 화면과 기능에만 쓴다. 다른 것에 번호를 붙이지 않는다.
- 완료 기준은 확인 가능한 문장으로 쓴다. 예: "목록에 최신순으로 10개씩 표시된다" (O), "목록이 잘 보인다" (X)
- 인터페이스 약속에는 요청과 응답의 실제 모양을 JSON 예시로 적는다. 필드 이름과 타입은 데이터 모델과 같게 쓴다.

```
# 설계 문서: (서비스 이름)

## 1. 개요
- 목적:
- 대상 사용자:
- 한 줄 소개:

## 2. 기능 목록
| ID | 기능 | 우선순위(필수/선택) | 완료 기준 |

## 3. 화면 구성
화면별로: ID, 이름, 목적, 주요 요소(버튼·입력·목록), 연결된 기능 ID, 이동하는 화면

## 4. 데이터 모델
엔티티별 필드와 타입

## 5. 인터페이스 약속
| 기능 ID | 메서드 | 주소 | 요청 | 성공 응답 | 오류 응답 |
그 아래 API마다 요청·응답 JSON 예시

## 6. 기술 스택
- 선택한 기술과 이유 한 줄씩 (테스트 도구 포함)
- 폴더: 소스 `src/`, 테스트 `tests/`, 서비스 문서 `docs/service/`
- 실행 명령: 의존성 설치, 서버 실행(주소와 포트 포함), 테스트 실행

## 7. 구현 순서
단계별로 포함할 기능 ID

## 8. 보안 고려 사항
인증, 입력 검증, 민감 정보 처리 등 점검할 항목

## 9. 미결 사항
```

문서를 다 쓴 뒤 전달하기 전에 스스로 점검한다.
- [ ] 모든 필수 기능이 어느 화면에든 연결되어 있다
- [ ] 모든 화면에 연결된 기능 ID가 있다
- [ ] 모든 완료 기준이 확인 가능한 문장이다
- [ ] 데이터 모델에 기능에 필요한 필드가 빠짐없이 있다
- [ ] 데이터를 저장하거나 불러오는 기능에는 모두 인터페이스 약속이 있다
- [ ] 인터페이스에 나오는 필드는 모두 데이터 모델에 있다
빠진 것이 있으면 고친 뒤 전달한다.

## 4. 전달
- `design.md` 파일을 전달한다.
- 마지막에 다음 단계를 안내한다: "이 파일을 프로젝트의 `docs/design.md`에 넣고, Claude Code에서 목업 단계를 실행하세요."
